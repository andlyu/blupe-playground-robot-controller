# SO101 follower

This source integration supports a configured SO101 follower with six STS3215
servos and an existing LeRobot calibration. The C++ process owns the serial bus;
Python runs the local panel, cloud camera uploader and IPC. The old YAM code path
is unchanged. Other drivers can implement `driver.RobotDriver`; the SO101 profile
currently defines five named degree joints and one gripper fraction.

## Install and configure

Use Python 3.10–3.12 and a C++17 compiler. On macOS install Xcode Command Line
Tools (`xcode-select --install`) if needed. The YAM `install.py` release installer
does not install SO101; use the source checkout:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[so101]'
.venv/bin/blupe-controller --config ./config.json setup \
  --hardware so101 --robot-id YOUR_ROBOT_ID \
  --api https://YOUR_SESSION_API --token-file /absolute/path/to/device-credential \
  --serial-port /dev/cu.YOUR_FOLLOWER \
  --calibration /absolute/path/to/lerobot/calibration.json \
  --camera front=0 --operator-port 8096 --camera-port 8089
.venv/bin/blupe-controller --config ./config.json doctor
.venv/bin/blupe-controller --config ./config.json probe
```

Linux uses a serial path such as `/dev/ttyACM0`. Use the follower’s port, not the
leader’s. Repeat `--camera wrist=1` to add cameras. The settings file is private
and setup refuses to overwrite it. Calibration is referenced, never rewritten.
Local tests may use a placeholder robot ID and credential path; publishing needs
the actual ID/token assigned by the operator dashboard. No token is required to
read positions or use the local panel.

`doctor` checks paths/dependencies without opening devices. `probe` compiles the
bundled native source into `~/.cache/blupe-controller/native/`, opens the serial
port exclusively, verifies servo models, homing offsets and position mode, and
reads positions. It issues **no servo writes**, including torque writes. A failed
probe must be resolved before using the panel. The arm must have motor power as
well as USB. Do not run another controller on the same bus.

## Local operator and cameras

Run these in separate terminals:

```sh
.venv/bin/blupe-controller --config ./config.json cameras
.venv/bin/blupe-controller --config ./config.json run
```

Open `http://127.0.0.1:8096/`. The panel starts read-only. **Enable** retains the
current position before enabling torque; **Move** accepts five angles in degrees
and a gripper fraction between 0 and 1. **Hold** stops target changes while
retaining torque. **Capture home** records the current pose in memory; **Move
home** uses the same motion limits. No universal home pose is assumed, and the
capture is cleared on restart.

The camera relay serves `http://127.0.0.1:8089/0` (MJPEG),
`/0/snapshot.jpg` (fresh JPEG) and `/status`. The operator panel previews snapshots.
On macOS allow camera access for the launching application when prompted. Verify
that the image is from the intended camera and that its counter keeps advancing.

With actual robot credentials, `publish-cameras` uploads fresh snapshots to
`/v1/robots/<robot_id>/cameras/<role>` through the existing publisher. Capture runs
in a different process from native motor communication. These uploads are not
the hosted HLS video publisher.

For a provisioned operator tunnel, configure `--operator-hostname` with the
hosted console’s hostname and use `connect-operator --local-port 8096` with the
assigned remote port/key/known-hosts file. The local panel binds only to loopback
and checks Host, Origin and a per-process control token. Hosting still requires
an administrator to assign the route and protect it with operator login. The
SO101 panel does not yet register for or execute cloud sessions; do not advertise
it as ready for queued tasks.

## Native behavior and commissioning limits

- The native loop targets 50 Hz, bounds interpolation to 100 encoder ticks/s
  (about 8.8 degrees/s), and rejects targets more than 228 ticks from current
  feedback (about 20 degrees; also applies to the gripper). Large home moves
  therefore need intermediate targets. This is not a hard real-time guarantee.
- All six targets must remain within calibration limits. Model, homing offset
  and position-mode mismatches fail startup. Calibration offsets already reside
  in the servos and are not applied twice.
- A 500 ms loss of Python heartbeats latches a hold. Feedback/protocol failures,
  invalid native commands, and tracking errors over 150 ticks latch a fault;
  a fault requires restarting the controller. Resume from hold requires an
  explicit enable. The loop continues polling while held.
- Hold, close and parent-process EOF retain the last bounded commanded pose;
  they never automatically release torque. Parent exit stops the native process
  after leaving that setpoint in the servos. USB loss, native crashes, power loss
  and mechanical faults cannot be corrected by this software.
- This driver does not implement collision avoidance, force limiting, or an
  independent hardware emergency stop. It does not rewrite servo gains/current
  limits. Validate the existing servo protection settings, supported arm posture,
  power cutoff and gripper force before physical commissioning. Holding torque
  is not an emergency stop.

Tests compile a separate PTY-only native binary that refuses real device paths.
They exercise the actual packet codec, calibration checks, limits, bounded speed,
fault latching, and watchdog behavior without motors. Run:

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

On the development Mac, USB enumeration confirmed the follower and an eMeet C950
at camera index 0. Servo READ probes got no reply, and camera capture was blocked
by macOS permission. Motion, actual images, Linux hardware and cloud publishing
have not been validated for this integration.
